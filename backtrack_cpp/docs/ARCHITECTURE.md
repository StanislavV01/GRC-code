# Реальна архітектура НРК (зі слів команди, 2026-07-30)

## Як комплекс працює сьогодні

```
Пульт (2 стіки; малий — 1 стік)
   │  зараз: інтернет/Ethernet · найближчим часом: ELRS
   ▼
Pixhawk 6C Pro (політник)
   │  CAN (шина DroneCAN)
   ├── Matek DroneCAN→PWM adapter
   ├── Ватметр Matek CAN-L4-BM
   ├── FlipSky FSESC 75450 ×2 (ходові)
   └── GPS M9N (DroneCAN)

CM4 — ТІЛЬКИ backtrack (companion). RS485 ВІДСУТНІЙ.
```

- Політник керує драйверами Flipsky по CAN.
- Failsafe політника зараз: при втраті зв'язку 2 с виконує останню команду → стоп.
- Живлення при піках не просідає.
- На борту крім двох ходових драйверів нічого силового немає.

## Вимоги до backtrack (нові вводні)

1. **Детекція зв'язку — тільки через статус політника.** Ethernet-сигнал не
   годиться, бо ELRS не має Ethernet-виходу. CM4 має питати політник, чи є в
   нього конект із пультом.
2. **Не писати весь маршрут від старту** — ковзний буфер за часом або
   пройденою відстанню (глибина = уточнити).
3. **Під час повернення** — кожен пройдений відрізок відстані перевіряти, чи
   з'явився конект у політника; якщо з'явився — віддати керування.
4. **Після прибуття в точку початку запису борт НЕ вимикати** — стояти
   увімкненим, щоб до нього можна було знову підключитись іншим способом.

## Наслідки для коду (що застаріло / що лишається)

| Модуль | Доля |
|---|---|
| `estimator` / `controller` (ядро) | **лишається без змін** |
| `hal/rs485_link` + протокол кадру оператора + `op_console` | **застаріло** (RS485 немає; канал керування — пульт→політник) |
| `hal/vesc_socketcan` (VESC-native CAN) | **під питанням**: шина — DroneCAN; чи говорять VESC-и VESC-native протоколом — питання 3 нижче |
| `hal/mpu9250_i2c` (GY-9250) | **під питанням**: у політника власні кращі IMU, доступні по MAVLink |
| `run_vehicle` стейт-машина | каркас лишається, але входи/виходи стають MAVLink |
| Детекція втрати зв'язку | замість тиші на RS485 — RC/GCS-failsafe статус політника по MAVLink |

## Уточнення (2026-07-30, друга ітерація)

- Зараз пульт = **QGC** (MAVLink GCS через інтернет). Пізніше ELRS (RC).
  Отже моніторити треба ОБИДВА failsafe: GCS і RC.
- Команда планує підключати **CM4 до бортової CAN-шини** (через MCP2515 HAT).
- Драйвери FSESC керуються політником **напряму по CAN** (без Matek PWM),
  тобто шина — DroneCAN, VESC у режимі UAVCAN/DroneCAN.

### Дві пастки CAN-only підключення CM4

**Пастка 1 — два майстри на одних ESC.** Під час backtrack CM4 мав би слати
esc.RawCommand тим самим драйверам, яким політник (armed, у failsafe) і далі
шле свої нулі. Два джерела команд упереміш = смикання моторів і
непередбачувана поведінка. Штатного «замовкни, тепер керую я» у DroneCAN
немає.

**Пастка 2 — статус лінка не живе на CAN.** ArduPilot не публікує стан
зв'язку з GCS/RC у DroneCAN. Слухаючи тільки CAN, CM4 не дізнається, що
пульт відпав, — а це тригер усієї функції.

### Рекомендована схема: CAN read-only + UART MAVLink

```
CM4 ── CAN (MCP2515) ──── шина DroneCAN: ТІЛЬКИ СЛУХАЄМО esc.Status
        └─> оберти/струм обох VESC = одометрія (без конфліктів, пасивно)

CM4 ── UART TELEM (MAVLink2) ── Pixhawk 6C Pro
        читає: heartbeat, RC_CHANNELS/GCS-статус (детекція втрати пульта),
               RAW_IMU/ATTITUDE (гіроскоп політника), режим/armed
        пише:  GUIDED + velocity/yaw-rate setpoints під час повернення;
               повернення в MANUAL при відновленні лінка
```

Керує моторами ЗАВЖДИ тільки політник; CM4 — його «порадник» по MAVLink.
Це штатний companion-патерн ArduPilot, жодних гонок на шині.

### ⚠️ Апаратне обмеження HAT

DroneCAN за замовчуванням в ArduPilot — **1 Мбіт/с** (CAN_P1_BITRATE=1000000).
MCP2515 з кварцом **12 МГц фізично не тримає 1 Мбіт/с** (мінімум 8 TQ на біт
недосяжний; треба 16 МГц). Отже або: (а) шина сконфігурована на 500 кбіт/с —
тоді ок, або (б) для CM4 потрібен інший CAN-HAT (16 МГц кварц / CAN FD,
напр. Waveshare 2-CH CAN HAT). Перевірити фактичний бітрейт шини!

## Цільова архітектура (пропозиція, під ArduPilot Rover)

```
CM4 ── UART TELEM2, MAVLink2 ── Pixhawk 6C Pro
        ▲ читає: heartbeat, RC/GCS link status, RAW_IMU (гіро),
        │         ESC telemetry / wheel odometry (джерело — питання 4),
        │         режим, armed
        ▼ пише:  при втраті лінка: режим GUIDED + setpoint (v, omega)
                 (SET_ATTITUDE_TARGET / SET_POSITION_TARGET velocity+yaw-rate)
                 при відновленні лінка: повернути режим MANUAL
```

- Трек пише CM4 своїм dead-reckoning (ковзний буфер).
- Повернення: pure pursuit на CM4, політник виконує (v, omega).
- Прибуття: HOLD/стоп, MAVLink-сесія жива, борт не вимикається.
