# План першого підключення CM4 до живої CAN-шини борта

Мета сесії (~30 хв чистого часу): нічого не зламати і зняти факти:
бітрейт шини, хто на шині, чи бачимо оберти VESC (наша одометрія),
хто шле команди моторам. **Ми тільки слухаємо** — listen-only режим
апаратно забороняє контролеру навіть ACK-ати кадри.

## 0. Передумови

- CAN_H/CAN_L з HAT заведені на шину борта (полярність!), земля спільна.
- **Термінатор 120 Ом на HAT НЕ вмикати** — шина борта вже термінована
  з двох боків; третій термінатор просадить рівні.
- Оверлей MCP2515 уже в config.txt (`./deploy/setup_cm4.sh` + reboot).
- Зібрати інструменти: `./build.sh` (на Pi) → `build/can_sniff`.
- Сервіси `vehicle`/`can0` НЕ вмикати — усе руками.

## 1. З'ясувати бітрейт (спроби від дефолту DroneCAN вниз)

```bash
sudo ip link set can0 down
sudo ip link set can0 up type can bitrate 1000000 listen-only on
# ЯКЩО ip повернув помилку "bitrate error" на 1000000 -> це наш HAT:
# MCP2515 з кварцом 12 МГц фізично не тримає 1 Мбіт/с. Див. розділ 5.
candump -td can0 | head        # або: ./build/can_sniff
```

Кадри сиплються рівним потоком → бітрейт вгаданий. Тиша або зростають
помилки:

```bash
ip -details -statistics link show can0    # дивитись bus-error, state
sudo ip link set can0 down
sudo ip link set can0 up type can bitrate 500000 listen-only on
candump -td can0 | head
# не пішло -> спробувати 250000, 125000
```

## 2. Інвентаризація шини

```bash
./build/can_sniff
```

Кожні 3 с — таблиця: вузол (node id), тип повідомлення, частота.
Очікуємо приблизно:

| Що | Тип | Хто |
|---|---|---|
| NodeStatus | 341 | усі вузли, 1 Гц — перелік живих node id |
| esc.RawCommand | 1030 | політник → мотори (частота = його цикл) |
| **esc.Status** | **1034** | **VESC-и → шина: ОБЕРТИ — те, за чим прийшли** |
| power.BatteryInfo / CircuitStatus | 1092/1091 | ватметр Matek |
| gnss.Fix2 | 1063 | GPS M9N |

Сфотографувати/зберегти вивід: `./build/can_sniff | tee ~/sniff_$(date +%H%M).log`

**Якщо сніфер лається на кадри з 11-бітними ID** — на шині щось не-DroneCAN
(VESC-native?). Це важливо, зберегти лог, розберемо.

## 3. Перевірка одометрії (головний результат сесії)

Машина на підставці або гусениці вивішені. Оператор із пульта плавно дає
малий газ уперед.

- `can_sniff` друкує рядки `esc.Status node X rpm ...` — **rpm мають
  ожити і рости зі стіком**, стояти на нулі при відпущеному.
- Визначити відповідність: node id ___ = лівий борт, node id ___ = правий
  (дати газ тільки одному боку, якщо режим дозволяє).
- Знак rpm при русі вперед: лівий ___ правий ___ (для дзеркального мотора
  очікуємо протилежні знаки).
- Частота esc.Status: ___ Гц (потрібно ≥20 Гц для одометрії; якщо менше —
  крутити параметр телеметрії ESC).

Якщо esc.Status НЕМАЄ взагалі → VESC-и не публікують телеметрію в
DroneCAN → увімкнути у VESC Tool (App Settings → UAVCAN → status rate)
або в параметрах політника. Без цього backtrack не має одометрії.

## 4. Що ще записати, поки все підключено

- `ip -details link show can0` — повний стан.
- 60 секунд сирого дампа для розбору вдома:
  `candump -l can0` (пише candump-XXXX.log; якщо candump немає —
  `./build/can_sniff --seconds 60 | tee ~/raw60.log`).
- Node id політника: ___ (вузол, що шле esc.RawCommand).
- Загальне завантаження шини (сума частот × ~100 біт / бітрейт): ___ %.

## 5. Якщо шина 1 Мбіт/с, а HAT її не тримає

Варіанти (рішення команди):
1. **Поміняти HAT** на 16 МГц/CAN-FD (напр. Waveshare 2-CH CAN HAT) —
   найчистіше, ~$15.
2. Знизити бітрейт усієї шини до 500к — правки у ВСІХ вузлах
   (політник CAN_P1_BITRATE, обидва VESC, Matek, GPS) — чіпає робочу
   конфігурацію, не рекомендую.
3. CM4 без CAN: одометрію брати через політник по MAVLink/UART
   (ESC_TELEMETRY) — тоді HAT взагалі не потрібен.
