# Питання по архітектурі НРК — v3

Закрито: пульт зараз = QGC (MAVLink через інтернет), потім ELRS. Політник
Pixhawk 6C Pro керує 2× FSESC 75450 **напряму по CAN** (DroneCAN). На шині
також: Matek DroneCAN→PWM, ватметр CAN-L4-BM, GPS M9N. CM4 планують чіпляти
на CAN. RS485 немає. Аналіз і рекомендована схема — `ARCHITECTURE.md`.

## Польові відповіді (2026-08-10, від оператора)

- **Мета проєкту уточнена:** backtrack — це **резервування (дублювання)
  інтернет-каналу керування** з польотником. Основний лінк — QGC через
  інтернет; коли він падає, CM4 має підхопити й вести НРК додому.
- **CM4 під'єднаний до Pixhawk 6C Pro по CAN** (та сама DroneCAN-шина, що ми
  цієї сесії підняли listen-only через Waveshare HAT). RS485 немає. CM4 вже
  фізично на шині — трафік бачимо (див. FIELD_NOTES 2026-08-10).
- **Питання «хто/як забирає керування моторами під час backtrack» — оператор
  НЕ знає.** Лишається блокером для команди (див. п.5).

- **Детекція втрати лінка — РІШЕННЯ Є:** у політника є статус, і CM4 **може
  його опитувати** (по CAN). Тобто CM4 стежить за статусом Pixhawk на шині;
  коли політник входить у GCS-failsafe (інтернет-лінк зник), CM4 це бачить і
  запускає повернення. → пів-блокера «як CM4 дізнається про втрату лінка»
  ЗАКРИТО (деталі: який саме месидж/поле статусу — треба звірити на живій шині;
  node 10 = політник, публікує NodeStatus (341) + купу vendor-типів 20xxx).
- **⛔ ДОКАЗ (mavlink2rest, 2026-08-10): MAVLink-лінка BlueOS↔автопілот НЕМАЄ.**
  У mavlink2rest (:6040) лише «vehicle 255» = сам BlueOS/GCS; єдине повідомлення —
  `PARAM_REQUEST_LIST`, яке BlueOS **шле** автопілоту (sysid 1) і **без відповіді**
  (~0.017 Гц ретраї). Ні HEARTBEAT, ні будь-чого від sysid 1. Тобто безпечний шлях
  «CM4 → GUIDED по MAVLink → автопілот» ЗАРАЗ ФІЗИЧНО НЕДОСТУПНИЙ. Єдиний канал
  CM4↔борт — DroneCAN, де автопілот активний майстер ESC (~130 Гц esc.RawCommand),
  тож прямий esc.RawCommand від CM4 = два майстри = небезпечно. **Реальний рух
  заблоковано до появи командного каналу** (вільний TELEM у CM4 → MAVLink, або
  MAVLink-over-CAN тунель). Це знову робить блокери #2 і #5 критичними.
- **Лишається відкритим — КОМАНДНА половина:** навіть знаючи про втрату лінка,
  по чистому CAN немає штатного способу віддати політнику GUIDED-команду
  «веди додому». Варіанти ті самі: MAVLink-over-CAN тунель (перевірити
  підтримку прошивкою) / окремий UART MAVLink / CM4 сам у CAN (два майстри —
  небезпечно). Оператор поки не знає, як забирається керування (п.5).

- **✅ Відповіді оператора (2026-08-10, друга партія):**
  - **Прошивка = ArduPilot** (Rover, ймовірно). → блокер #1 закрито.
  - **Вільних TELEM/serial НЕМАЄ.** Pixhawk має 2 CAN-порти; **CM4 під'єднаний по
    CAN1** — на тій самій DroneCAN-шині, що й ESC (збігається зі сніфером).
  - **Наслідок — перспективний шлях БЕЗ нового заліза:** ArduPilot підтримує
    **MAVLink поверх CAN (DroneCAN tunnel)**. Тобто командний канал CM4↔політник
    можна підняти по вже наявному дроту CAN1: ArduPilot тунелює MAVLink через
    DroneCAN, BlueOS/mavlink-router чіпляється до тунелю → з'являється GUIDED.
    Автопілот лишається єдиним майстром моторів (безпечно). ПОТРІБНО:
    (1) увімкнути/налаштувати MAVLink-CAN тунель у параметрах ArduPilot;
    (2) навчити BlueOS ходити в цей тунель (зараз mavlink2rest порожній —
    транспорт не підключений). Обидва — конфіг, не залізо.
  - Q про інтернет-модем: відповідь «S-bus» — уточнити (SBUS зазвичай RC, не
    MAVLink; можливо, керування з пульта йде RC-каналом, а не GCS-телеметрією).
  - **ПОТРІБЕН експорт параметрів ArduPilot** (QGC → Parameters → Tools → Save,
    або `param show CAN*`) → з нього видно конфіг CAN-портів, чи ввімкнено тунель,
    failsafe, skid-steer. З цього сплануємо командний канал. Поки експорту немає —
    реального руху не робимо.

## Знахідки з pixhawk-6c-pro.params (2026-08-10)

Файл параметрів у репо: `pixhawk-6c-pro/pixhawk-6c-pro.params` (+ ArduPilot Lua
у `pixhawk-6c-pro/APM/scripts/`).

- **ArduPilot Rover.** Автопілот = DroneCAN **node 10** (`CAN_D1_UC_NODE=10`).
  **CAN1 @ 1 Мбіт** DroneCAN (`CAN_P1_DRIVER=1`, `CAN_P1_BITRATE=1000000`,
  `CAN_D1_PROTOCOL=1`); **CAN2 вимкнено** (`CAN_P2_DRIVER=0`). ESC по DroneCAN
  (`CAN_D1_UC_ESC_BM=3`).
- **MAVLink у автопілот вже є:** SERIAL1 і SERIAL2 = MAVLink2 (`SERIALx_PROTOCOL=2`)
  — це зайняті TELEM (джойстик/модем). BlueOS/CM4 туди НЕ під'єднаний (mavlink2rest
  порожній). SERIAL7 = RCIN (протокол 23). RC увімкнено (`RC_PROTOCOLS=1`).
- **Скриптинг увімкнено** (`SCR_ENABLE=1`). Lua `tst.lua` приймає MAVLink
  `MANUAL_CONTROL`/`HEARTBEAT` і мапить кнопки на сервоприводи (ніж/шарнір/гак/
  лебідка) + engine-enable; має safety-таймаут 2 с (усе в нейтраль).
- **Failsafe:** GCS-loss 5 с (`FS_GCS_ENABLE=1`, `FS_GCS_TIMEOUT=5`) → **Hold**
  (`FS_ACTION=2`). Тобто ЗАРАЗ при втраті лінка борт просто **зупиняється**, не
  вертається. RC/throttle failsafe теж увімкнено.
- **Ключ до командного каналу:** `CAN_D1_UC_SER_EN=0` — DroneCAN **serial-тунель
  ВИМКНЕНО**. Це і є механізм «MAVLink/serial поверх CAN». Увімкнення (=1) +
  прив'язка SERIALx до тунелю + CM4 як інший кінець → MAVLink CM4↔автопілот по
  наявному CAN1.

## Рішення: як backtrack керуватиме (обрати A/B/C)

- **A. CM4 → MAVLink-over-CAN тунель → GUIDED.** Увімкнути `CAN_D1_UC_SER_EN` +
  serial-тунель, CM4 шле автопілоту швидкість (GUIDED). Автопілот — єдиний майстер
  моторів. Плюс: наш dead-reckoning-мозок керує, повний контроль логіки. Мінус:
  треба тунель-клієнт на CM4 + param-зміни; складніше.
- **B. Рідний ArduPilot Rover SmartRTL.** Автопілот сам пише трек і вертається
  (змінити `FS_ACTION` на SmartRTL). Плюс: нуль нового коду, перевірена функція.
  Мінус: залежить від оцінки позиції автопілота в GNSS-глушняку (чи довіряємо
  wheel-odometry+IMU dead reckoning ArduPilot); менше контролю; наш CM4-мозок стає
  резервом, а не основним.
- **C. Lua на автопілоті.** Backtrack як скрипт на борту (як уже роблять аукс-Lua).
  Плюс: без нового заліза/каналу. Мінус: Lua обмежений, писати dead-reckoning на
  ньому важко; дублює наш C++ мозок.

Рекомендація для GNSS-denied незалежності — **A** (наш мозок + автопілот як
безпечний актуатор). Але це рішення команди; від нього залежить, куди йде код далі.

## Блокери (без цього не пишемо код)

1. **Прошивка політника: ArduPilot Rover чи PX4? Версія?**
   (QGC працює з обома — це не відповідь на питання прошивки.)

2. **Чи вільний на політнику хоч один UART (TELEM1/TELEM2) під CM4?**
   Через що зараз заходить інтернет-лінк QGC — який модем, у який порт
   політника він встромлений?
   Причина: статусу зв'язку з пультом НА CAN-шині НЕМАЄ — ArduPilot не
   публікує його в DroneCAN. Для детекції втрати лінка і для передачі команд
   повернення потрібен MAVLink, тобто UART. CAN лишається для одометрії
   (слухати оберти VESC).

3. **Який бітрейт CAN-шини: 1 Мбіт/с (дефолт DroneCAN) чи 500 кбіт/с?**
   Наш HAT (MCP2515, кварц 12 МГц) фізично НЕ працює на 1 Мбіт/с.
   Якщо шина 1М — купуємо інший HAT (16 МГц / CAN FD) або знижуємо шину.

4. ✅ **ЗАКРИТО (стенд-тест 2026-08-10).** Одометрія = DroneCAN `esc.Status`
   (тип 1034) від **node 50**; **esc_index 0 = ЛІВА гусениця, esc_index 2 =
   ПРАВА**; знак rpm «+»=вперед. Підтверджено послідовністю
   вперед/назад/розворот-вліво/вправо (див. FIELD_NOTES 2026-08-10 та
   `field_logs/2026-08-10/standtest2_analysis.md`). HAL `vesc_socketcan`
   (VESC-native left=1/right=2) НЕ відповідає борту — переписати під це джерело.

5. **Під час backtrack хто керує моторами?**
   Наша пропозиція: ЗАВЖДИ політник; CM4 шле йому GUIDED (v, omega) по
   MAVLink. Альтернатива "CM4 сам шле esc.RawCommand по CAN" створює двох
   майстрів на одних ESC (політник у failsafe продовжує слати нулі) —
   потрібно явне рішення команди.

6. **Чи можна змінити failsafe політника** з "2 с → стоп" на
   "2 с → стоп → CM4 переводить у GUIDED і веде додому"? Хто тримає
   параметри політника?
